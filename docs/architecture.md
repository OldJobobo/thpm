# Architecture

> New to the codebase? Start with the [visual architecture map](architecture-map.md), then use this document as the detailed contract.

THPM has five deliberately narrow layers:

1. `thpm` owns registry state, capability checks, locking, migration, and JSON responses.
2. Omarchy owns palette parsing and template rendering. THPM places opted-in `.tpl` files in `~/.config/omarchy/themed`; Omarchy emits their generated files into the active theme.
3. A theme hook at `~/.config/omarchy/hooks/theme-set.d/90-thpm` invokes integration adapters after a theme switch; a separate `post-update.d/90-thpm-ui` hook preserves the graphical manager's self-healing launch route.
4. The QML control panel is a normal compositor-managed `FloatingWindow` and a client of `thpm --json`; it does not duplicate registry or persistence logic or implement its own window-management gestures.
5. The Textual TUI runs through `thpm tui` and calls the same Python `Service` in background workers, keeping the interface responsive without creating a second state or mutation path.

The canonical palette is the active Omarchy 4 `colors.toml` as resolved by `omarchy-theme-color --all`. Templates use the resolver's canonical long background/foreground names. At the Python boundary, THPM maps those canonical names to its private short-key TUI schema before validation; non-empty canonical values take precedence over conflicting short compatibility values, while empty canonical rows are treated as absent. THPM does not maintain a second alias/derivation cascade and never derives state from generated application files.

Plugin state is stored in `$XDG_STATE_HOME/thpm/state.toml`; user-editable behavior is stored separately in `$XDG_CONFIG_HOME/thpm/config.toml`. The versioned config currently selects `behavior.restart_policy = "automatic" | "notify"`, defaults to `automatic`, and falls back to notify-only behavior with an explicit warning when malformed. Mutations use an advisory runtime lock and atomic replacement. Each hook adapter runs behind an error boundary so one integration cannot abort the remaining plugins. Adapter results distinguish applied, unchanged, skipped, and failed work; hook responses include per-status counts, changed paths, actions, optional durations, structured `restartRequired` application names, warnings, and errors. The hook sends one best-effort desktop notification when unresolved restarts remain. `Service.run_theme()` marks its private hook environment for forced reload, distinguishing an explicit **Apply active theme** request from an ordinary no-op theme event without changing the public hook arguments. The installed wrapper sends the live human integration outline and final report to stderr because Omarchy discards hook stdout. `thpm run` gives the wrapper two private runtime paths: an append-only JSON Lines event channel for integration start and finish notifications, and a final JSON report that remains authoritative for results and exit status. The parent consumes events while Omarchy is still running, captures Omarchy output without pipe deadlocks, and renders the final report without executing adapters twice. Event delivery is presentation-neutral and best-effort; it never replaces the final report contract or decorates `--json` output. Readiness checks are shared by snapshots, enable policy, Doctor, and hook execution so a plugin cannot appear actionable to one caller and inert to another. Before copying a THPM-generated fallback, readiness and application both reject unresolved Omarchy template placeholders; theme-provided assets remain authoritative and bypass that generated-file check.

The authoritative final outcomes are also appended best-effort to a separately locked, mode-`0600`, size-rotated JSON Lines journal under `$XDG_STATE_HOME/thpm/logs`. Its lock and data files reject symlinks and non-regular files. This journal contains bounded structured metadata rather than raw environments, configuration contents, or unbounded command output, and an observability failure never changes operation success. `thpm report` reads bounded recent entries and Doctor output into a separate versioned support-report schema, normalizes embedded home paths, redacts secret-like and authorization values plus URL userinfo/query/fragment data, and writes mode-`0600` JSON under THPM state unless the caller chooses another output path.

Omarchy-native behavior is outside THPM. Foot, tmux, GNOME mode/icons, Marketplace and generated VS Code-family themes, general Obsidian theming, keyboard theming, and Omarchy terminal reload behavior are displayed as native read-only records. The separate Obsidian Terminal community plugin remains THPM-owned because Omarchy's native Obsidian handler only installs the application CSS theme and does not synchronize the plugin's xterm.js palette. Two conditional compatibility integrations run after those native handlers: managed GTK CSS deployment and validated theme-only local editor extension installation. They are non-applicable, not unhealthy, when the active theme does not request those capabilities.

Source updates use stable GitHub release assets with a mandatory SHA-256 companion file. A new runtime is staged and validated before atomic activation; activation-time reconciliation or UI-installation failures restore the previous runtime and THPM-owned integration files. The active theme is refreshed only after activation commits. A post-commit refresh failure does not roll back the runtime; it returns a partial-failure result with `thpm reconcile --refresh` as the recovery command.

Template-schema migrations use versioned per-user markers under `$XDG_STATE_HOME/thpm/migrations` and a separate migration lock. Installation always requests an active-theme refresh, while normal reconciliation completes a pending migration or refreshes when explicitly requested. Pacman-owned installations are never overwritten. Human AUR upgrades run synchronously in the invoking terminal with package-manager confirmations disabled and refresh theme output afterward. Interactive callers without an attached terminal can open an Omarchy terminal; JSON callers instead receive `requires-interactive` and never launch or prompt.

Source runtimes are private virtual environments containing THPM and an exact transitive dependency set from `requirements-source.lock`. Both source installation paths require hashes and universal wheels, and CI resolves the lock on every supported Python version. Staged updates install the locked dependencies and import the TUI before activation, so a dependency or frontend failure participates in the same rollback boundary as integration reconciliation. Arch packages use the system `python-textual` package instead.

The TUI reads the active semantic `colors.toml` when it starts and on manual refresh. Palette errors select a bundled fallback theme and are reported as degraded presentation, not as a fatal application error.

Omarchy Menu owns one THPM entry. Its target is selected by `thpm ui surface` or the Menu launcher control in either frontend and persisted in `$XDG_STATE_HOME/thpm/ui.toml`; the CLI, GUI, and TUI all use the same service operation. The GUI action invokes `thpm ui open`, not Shell summon IPC directly. Under a serialized launch lock it compares the packaged and deployed frontend generation, stages and switches a complete tree when necessary, rescans and verifies discovery, repairs and verifies enablement, summons the panel, and calls the panel's `health` method until asynchronous QML loading acknowledges a visible window. Exit code zero with any IPC response other than the documented success value is a failure. If graphical readiness cannot be established, an interactive launch opens `thpm tui` in a floating terminal as a functional degraded surface; JSON callers receive the failure without spawning UI.

`thpm install` installs `post-update.d/90-thpm-ui`, whose idempotent `thpm ui sync` preserves the stable launcher only when the graphical manager is already installed. Omarchy runs this user hook before its AUR phase, so package assets installed later in that update are synchronized by the stable launcher's click-time repair. Source self-updates continue to synchronize the panel during their transactional update path.
