# Plugin contract

This is a maintainer reference for built-in integration contracts. Users can inspect the current list with `thpm list`, check problems with `thpm doctor`, and enable an integration with `thpm enable <id>`. Asset names such as `zed.json` or `gtk.css` refer to files supplied by the active Omarchy theme. Availability is not a support claim: the [integration support register](integration-support.md) records certification status, reference platform baseline, outstanding real-application gates, and retired adapters. Every currently active adapter is Experimental and default-disabled for new state until promoted with complete evidence. Existing schema-1 `true` values are grandfathered because the old format cannot distinguish inherited defaults from explicit choices; they are not proof of opt-in. Cava remains separately gated by its consent marker.

Plugins are records in `src/thpm/registry.py` and adapters in `src/thpm/integrations.py`. A plugin may consume an Omarchy-rendered THPM template, a theme-provided optional asset, or perform a guarded external action. Every adapter reports an explicit `applied`, `unchanged`, `skipped`, or `failed` outcome; an empty change list is never treated as evidence that work succeeded. Ordinary theme hooks run reload commands and structured `restartRequired` notices only after managed content changes, so no-op reconciliation does not probe inactive applications or emit false action requirements. Explicit reapplication through `thpm run` or a frontend's **Apply active theme** control sets a private force flag so restart-required adapters such as Spotify actually run even when their files are current. The user preference at `$XDG_CONFIG_HOME/thpm/config.toml` selects `automatic` or `notify` restart policy for apps with a safe restart adapter. Conditional compatibility integrations also report whether the active theme makes them applicable.

Rules:

- Read colors only from the active Omarchy 4 `colors.toml` contract.
- Do not write files owned by an Omarchy-native integration.
- Preserve user-owned content; use a clearly delimited managed block when editing a shared file.
- Treat a missing optional application as unavailable. When an enabled asset-only integration loses its theme asset, relinquish its managed output and restore the displaced file or application default.
- Reload only the application the adapter owns, bound the command with a timeout, and report nonzero exits.
- Add behavioral tests for paths, generated files, and preservation behavior.

Template names start with `thpm-` and end in `.tpl`. Omarchy renders each into the active theme without the `.tpl` suffix. An adapter then atomically installs that generated output where the application expects it.

The opt-in Pi hot-reload compatibility integration is an action-only adapter for Omarchy's native Pi theme output. Omarchy atomically replaces `~/.pi/agent/themes/omarchy-system.json`, while Pi's live watcher responds to a metadata change for the active custom theme. After the native theme command finishes, THPM verifies that the installed file exactly matches the current theme's `pi.json`, then advances only its modification time without rewriting its contents, access time, or inode. A stale native output is skipped without emitting an event, symlink sources and targets are refused, and missing prerequisites follow normal readiness reporting. The event applies only to sessions currently using `omarchy-system`; THPM does not claim that sessions with project, CLI, automatic, or in-memory theme overrides repainted.

The Obsidian Terminal integration is distinct from Omarchy's native Obsidian application theme. It discovers the Terminal community plugin's `data.json` through Obsidian's vault registry, common vault roots, or `OBSIDIAN_VAULT_PATH` / `OBSIDIAN_TERMINAL_DATA_JSON` overrides. Direct data-file overrides must still identify an exact `.obsidian/plugins/terminal/data.json` path, and no path component may be a symlink. It validates every settings document before changing any of them, preserves unrelated plugin and profile options, atomically replaces only `terminalOptions.theme` with the active semantic palette, and disables each profile's `followTheme` override so the plugin cannot immediately replace that xterm palette with Obsidian CSS colors. THPM records only profiles it changes from following the application theme and guardedly restores those fields when the integration is disabled or THPM is uninstalled; profiles already configured not to follow the application theme remain user-owned. Symlinked or malformed settings and restoration state are refused. Temporarily missing or unwritable vault settings retain their restoration records and produce structured incomplete-cleanup recovery details instead of reporting false success. Because the running plugin does not reliably reload external settings changes, changed settings report Obsidian as restart-required.

The Discord integrations are mutually exclusive. `discord` prefers a theme-provided `vencord.theme.css` and otherwise renders an Omarchy palette wrapper around THPM's vendored Midnight base. The base is derived from `refact0r/midnight-discord` under the MIT License and hosted from this repository for the generated stylesheet to import. That fallback requires network access and intentionally follows the hosted `main` artifact, allowing selector-only compatibility repairs between THPM package releases; upstream imports are pinned and reviewed through `scripts/update-vencord-base.sh`. `discord-system24` follows the same asset-first pattern with `vencord-system24.theme.css` and its generated System24 fallback. Both install the selected output as `vencord.theme.css` in existing supported client theme directories.

The Zellij adapter generates a complete `thpm-current` theme from the active semantic `colors.toml` palette and prefers a theme-provided `zellij.kdl` as an authored override. It writes the result to Zellij's configured theme directory, selects it in `config.kdl`, and removes the delimited inline block used by pre-1.0 THPM. After changing the external theme, THPM waits for a strictly newer wall-clock second when necessary and atomically rewrites the selected `config.kdl`, ensuring Zellij's polling config watcher reparses the completed theme and updates running sessions without leaving future-dated configuration files. The adapter honors `ZELLIJ_CONFIG_FILE` and `ZELLIJ_CONFIG_DIR` when a custom config declares an absolute root-level `theme_dir`; relative theme directories and custom configs without that declaration are rejected because Zellij resolves them inconsistently between startup and watcher reload. Per-invocation `--config` and `--config-dir` flags cannot be discovered by a persistent theme hook. When neither palette nor authored asset is available—or when the integration is disabled—THPM restores the previously selected theme and any file displaced at `thpm.kdl`. Targets changed outside THPM and untracked legacy targets are preserved. Disable and uninstall report a restart for running same-user Zellij processes only when managed Zellij configuration or theme output actually changed.

The GTK compatibility integration synchronizes an active-theme `gtk.css` into THPM-owned GTK 3 and GTK 4 stylesheets and inserts delimited imports into user CSS. It removes only those managed files and blocks when the next theme does not request GTK CSS or the integration is disabled. Doctor remains read-only but reports unmanaged GTK stylesheets—including recognizable Aether output—because they can override Omarchy after a theme switch. On the live desktop it also compares GNOME mode, Adwaita theme, icons, and the portal color preference with the active theme, and flags the legacy `gtk-application-prefer-dark-theme` setting that libadwaita ignores.

Branding and cliamp are asset-only integrations. Before their first takeover, THPM records whether the destination existed and preserves its contents. If a later theme omits the asset—or the integration is disabled or THPM is uninstalled—THPM restores that prior file or removes its own destination so the application can use its default. Branding tracks `about.txt` and `screensaver.txt` independently. A destination edited outside THPM after installation is preserved rather than overwritten during cleanup.

cliamp owns its normal theming through contrast-checked built-in themes or its terminal-ANSI default. THPM does not generate a custom cliamp theme from `colors.toml`, because cliamp's smaller custom schema cannot preserve all of the independent foreground/background roles used by its native styles. A theme author can deliberately override native behavior by shipping `cliamp.toml` with the exact line `# thpm:cliamp-use-native`. Only that marked file is installed restorably as `~/.config/cliamp/themes/omarchy.toml`, and THPM selects `omarchy` in cliamp's top-level config. Removing the marker or asset, disabling the integration, or uninstalling THPM restores the displaced file and prior theme selection. Later user edits or selections are preserved rather than overwritten.

SwayNC support is retired because the former adapter copied `colors.css` without proving that SwayNC's loaded `style.css` imported or consumed it. It no longer appears in the active registry. Reconciliation and uninstall retain guarded cleanup for the historical `~/.config/swaync/colors.css` destination, preserving unknown and user-modified files.

Typora is an Experimental, default-disabled active integration. It installs the current Omarchy theme as `~/.config/Typora/themes/thpm.css`, preferring an authored `typora.css` and otherwise using the generated `thpm-typora.css`. Guarded legacy cleanup remains for the historical `~/.config/Typora/themes/omarchy.css` destination, restoring tracked displaced content and preserving unknown or user-modified files.

Windsurf support is retired and no longer appears in the active integration registry. The editor was replaced by Devin Desktop, whose command, profile, and extension lifecycle no longer match the former Windsurf contract. Reconciliation and uninstall retain guarded legacy cleanup for THPM's old `.windsurf/extensions/local.omarchy-theme/themes/omarchy.json` destination; unknown and user-modified files remain preserved.

Vicinae support is retired and no longer appears in the active integration registry. Reconciliation and uninstall remove its rendered template and restore or relinquish THPM's former `thpm.toml` outputs under both `${XDG_DATA_HOME:-~/.local/share}/vicinae/themes/` and `~/.config/vicinae/themes/`, preserving user-modified files and tracked displaced content.

The persisted `zed-extra` integration is presented as **Zed authored theme**. It prefers `zed.json`, falls back to `aether.zed.json`, and validates a regular non-symlink UTF-8 JSON file no larger than 1 MiB. The root must contain exactly one dark or light theme with a style object. THPM preserves the schema, author, appearance, and style while normalizing the package and theme names to **THPM Current**, installed restorably at `~/.config/zed/themes/thpm-current.json`. The former `omarchy.json` destination is migrated only through restoration metadata or a positive legacy-content match; unknown and user-modified files are preserved. THPM never modifies `aether.json`, `omazed.json`, or Omazed hooks.

Run `thpm enable zed-extra` to persistently synchronize authored Zed themes after theme changes. Enabling it through the CLI, TUI, or graphical manager also performs the one-time settings operation. `thpm zed setup` exposes only that direct installation and settings-selection step; it does not persistently enable synchronization. The settings operation backs up existing Zed settings once under THPM state and uses a token-aware JSONC edit to select **THPM Current** while preserving comments and keys outside the replaced theme value. Theme hooks never rewrite settings. `thpm zed status` reports source precedence, synchronization, the selected string or light/dark theme, and Omazed command/output availability. Omazed remains an independently owned generated fallback; when no authored source exists, THPM reports that the user may select **Omazed** rather than claiming an automatic switch.

Generated and hybrid integrations use the same displaced-file tracking. Disabling or uninstalling one restores its previous destination and removes its rendered `thpm-*` output; browser cleanup also removes only THPM's delimited `userChrome.css` import. For installations upgraded from versions without restoration metadata, THPM removes a legacy destination only when its contents positively match a current generated output or a locally installed theme asset. Unknown files are preserved, and each legacy path is checked only once. Spotify also migrates tracked output from its former destination before taking ownership at the current path.

Spotify writes `~/.config/spicetify/Themes/omarchy/color.ini`, initializes the companion `user.css` from THPM's bundled Omarchy stylesheet when it is missing, and selects `current_theme = omarchy` with `color_scheme = Base` through Spicetify's CLI. Existing stylesheets are never overwritten or removed. It requires a completed, current Spicetify backup before becoming actionable; Doctor reports the one-time backup command when that prerequisite is absent and treats a different active theme as repairable setup rather than unavailability. Hooks never initiate Spicetify's first-time backup. After setup or a changed palette, THPM runs `spicetify refresh`. Because Spicetify 2.44 does not inject refreshed colors into the existing webview, an already-running client is either restarted with `spicetify restart` under the `automatic` policy or returned as `restartRequired = ["Spotify"]` under `notify`; a closed client remains closed and needs no notice.

Steam theming uses the external steam-adwaita installer with `--color-theme omarchy`; Steam has no in-app theme selector for this integration. After a successful apply, THPM reports `restartRequired = ["Steam"]` only when the Steam process is running. THPM does not terminate Steam because doing so could interrupt games or downloads; fully exit and relaunch the client to load the patched stylesheet. A closed client receives no restart notice and loads the theme on its next launch.

The local editor compatibility integration handles `local.*` descriptors backed by `vscode-extension/`. It validates that the package is a data-only theme extension, verifies descriptor/manifest identity and the contributed label, builds a deterministic temporary VSIX, and installs it only when its source hash changed or the extension is absent. Executable extensions, arbitrary contributions, symlinks, unsupported files, and prebuilt VSIX bundles are rejected.

Cava requires version 0.10.6 or newer and is opt-in because setup changes its `[color] theme` selector to `thpm`. Legacy state files that saved Cava's former enabled-by-default value are masked until successful confirmed setup writes a durable opt-in marker; failed setup rolls that marker back, while disable retains it for later confirmed re-enablement. The selector edit is line-preserving and separately tracked so disable and uninstall can restore only the previous selector while retaining unrelated config changes and symlinked dotfile layouts. Cava still prefers a theme-provided `cava_theme` over its generated fallback. Doctor reports stable checks for the executable, version, config, selector, source, installed target, and running processes; `thpm doctor cava --fix` applies only a confirmed repair. Reload uses PID-specific `SIGUSR1` only for processes confirmed to use the managed config and theme directory, never a broad `pkill`. Maintainers can run `scripts/cava-live-test.sh` for a non-destructive real-Cava launch and reload check in an isolated XDG sandbox; it intentionally does not claim visual verification or dry-run validation.

Authoritative hook outcomes and Cava lifecycle operations are copied best-effort into a bounded structured journal at `$XDG_STATE_HOME/thpm/logs/operations.jsonl`. Journal failure cannot fail an integration. `thpm report [plugin] [--output PATH]` combines filtered recent outcomes with Doctor checks, application/runtime versions, active theme, plugin state, and metadata/digests for known files. It deliberately excludes file contents, raw process environments, host identity, unrelated arguments, and unbounded subprocess output; report JSON carries its own `reportSchemaVersion` independently of the CLI envelope.

Firefox and Zen require an initialized default browser profile, prefer their theme-provided CSS before generated CSS, and report both the managed stylesheet and `userChrome.css` import. Superfile prefers its declared theme asset before the generated fallback. Discord requires a supported client theme directory, and Steam requires the steam-adwaita installer. GTK applications cannot be restarted generically without risking unsaved work, and nwg-dock-hyprland has no authoritative relaunch command that preserves its original flags. Both therefore remain in `restartRequired` after relevant file changes under either policy instead of being killed unsafely.

Thunderbird requires an initialized default profile discovered the same way as Firefox and Zen, prefers a theme-provided `thunderbird.css` before generated CSS, and installs the single managed stylesheet under the profile's `chrome/` directory. Since Thunderbird's message list, folder pane, and reading pane render as separate `about:3pane`/`about:message` content documents rather than the outer chrome window, the managed stylesheet targets both cascades and is imported into both `chrome/userChrome.css` and `chrome/userContent.css` through identical delimited blocks; disable and uninstall clean up both. Because one file serves both entrypoints, every rule in it is scoped: outer-chrome rules sit inside `@-moz-document url-prefix("chrome://")` and content rules inside `@-moz-document url("about:3pane"), url("about:message")`, so the file is inert in whichever entrypoint it does not apply to and never leaks chrome declarations into mail content. Both entrypoints are resolved before either is written, so a malformed managed block cannot leave a partial install behind; a symlinked entrypoint is refused rather than replaced with a regular file, and an existing entrypoint's permissions are preserved. Thunderbird has no supported live reload for `userChrome.css`/`userContent.css`, so it remains in `restartRequired` after relevant file changes, matching Firefox and Zen.

Beyond the shared `--layout-*`/`--selected-item-*` design tokens, the generated CSS sets the same custom properties that Gecko's `LightweightThemeConsumer` would set from an installed theme add-on. Most of those are consumed as plain `var()` lookups rather than behind the `:root[lwtheme]` attribute that only that consumer can set, so a plain stylesheet reaches them: `--toolbar-background-color`, `--toolbar-text-color`, `--toolbarbutton-icon-fill`, `--toolbar-field-*`, `--panel-*`, `--sidebar-*`, `--autocomplete-popup-highlight-*`, `--chrome-content-separator-color`, and the `--lwt-toolbarbutton-*` group. `#navigation-toolbox` (the menu bar / unified toolbar / tab strip container) needs a direct override instead, because `messenger.css` only colors it from `--lwt-accent-color`/`--toolbar-background-color` under `:root[lwtheme]` and otherwise falls back to the native `-moz-headerbar`/`ActiveCaption` system color.

What stays out of reach is the genuinely `[lwtheme]`-gated remainder: `--lwt-accent-color` is consumed under the attribute in most of its uses and `--lwt-selected-tab-background-color` in all of them, so window-frame accent and selected-tab tinting cannot be fully reproduced without a theme add-on. That is a hard ceiling, not something more selector-hunting would close.

Accent colors render through `{{ gradient_start accent blue }}` rather than a direct `accent` reference. `accent` is `OPTIONAL_HEX` in `src/thpm/palette.py`, not `REQUIRED`, and a template referencing it directly would render literally on a palette that omits it, which THPM rejects as an unresolved placeholder. Omarchy's `gradient_start` resolver takes an explicit fallback reference, so the token resolves to the theme's real accent when the palette defines one and to `blue` when it does not, and always renders to a hex color. (`thpm-firefox.css.tpl` still substitutes `blue` unconditionally; the same approach would apply there.)

For users who want fidelity beyond that ceiling — every `[lwtheme]`-gated surface, and live theme switching without a restart — [omarchy-thunderbird-theme](https://github.com/jfuerwentsches/omarchy-thunderbird-theme) drives Thunderbird's actual WebExtension theme API via a sideloaded extension and a native-messaging bridge, at the cost of that extension/process footprint. This integration is the lighter-weight, no-extension alternative, not a drop-in replacement for it.
